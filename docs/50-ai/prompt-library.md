# 任务提示模板

> 状态：已确认
> 最后更新：2026-11-08
本文范围：可直接复制的任务提示模板。流程与门禁见 [change-protocol.md](change-protocol.md) 与
[definition-of-done.md](definition-of-done.md)。

## 使用方式

模板只提供任务结构，不替代阅读文档。复制后在尖括号处填入具体范围；不确定的契约先提问，不要让代理自行假设。

## 新增功能

```text
目标：<一句话说明用户可见的能力>。
范围：<涉及模块 / 页面 / 端点>。
请先按 AGENTS.md → docs/README.md 定向，再判断改动类型：
- 需要规格就写 docs/40-specs/ 草案并列出验收标准；
- 涉及契约/DDL/调度/认证就先登记待确认项，确认后再实现。
实现顺序：契约 → 数据访问 → 服务 → 接口/前端；补测试并运行 ./scripts/verify.sh。
交付时给出结论、改动、实际验证输出、差异与未覆盖项。
```

## 写规格

```text
功能：<用户可见能力>。
范围：<涉及模块 / 页面 / 端点；明确不做什么>。
请按 docs/40-specs/README.md 的模板起草规格：目标、非目标、用户场景、契约、验收标准、边界与异常。
验收标准必须能直接写成测试；未定契约标【待确认】并在 docs/20-adr/README.md 登记。
只写规格，不先写实现；确认后再进入代码阶段。
```

## 写 ADR

```text
决策：<要用一句话记录的决策>。
背景与约束：<为什么现在必须决定、有哪些限制>。
请先读 docs/20-adr/README.md 的模板与“什么时候必须写”，起草 ADR 草案：
背景、备选项（至少两个，含代价）、决策、后果与重新评估触发条件。
草案需项目所有者确认后才实现；确认前不得把方案写成既定事实。
```

## 修复缺陷

```text
现象：<可复现步骤、期望、实际>。
影响：<模块 / 数据 / 用户>。
请先复现并定位根因，最小化修改；补回归测试，不得删除或弱化现有测试。
如果根因涉及未确认的契约或需要改数据模型，先停下来说明，不要自行扩大范围。
完成后运行 ./scripts/verify.sh 并给出原始输出。
```

## 重构

```text
范围：<文件 / 模块>。
约束：外部行为完全不变；不引入新依赖；不顺手改无关代码。
请先说明重构边界与验证方式，再分小步实施。
完成后必须给出测试全绿的实际输出，并在提交信息中注明“行为不变”。
```

## 文档更新

```text
目标：<要修正/新增的事实>。
请先查 docs/README.md 的“唯一权威分工”，确定唯一来源；其他位置只加链接，不复制正文。
同步目录索引、状态块、待确认清单；新增架构文档按 docs/10-architecture/README.md 的骨架写。
完成后运行 ./scripts/verify.sh（或至少四个文档检查脚本），并给出实际输出。
```

## 排查环境问题

```text
现象：<报错原文 / 复现步骤>。
期望：<应该发生什么>。
实际：<实际发生什么，已尝试过哪些命令>。
请先按 docs/30-guides/dev-workflow.md「环境排错」与 docs/30-guides/getting-started.md 核对环境，
给出最小复现命令与原始输出；不要先改代码，也不要用跳过检查的方式绕过。
```

## 代码审查

```text
审查范围：<PR / 提交 / 文件>。
请按以下顺序检查：
1. 是否违反 AGENTS.md 红线；
2. 是否删除/弱化测试，是否有回归测试；
3. 契约/DDL/调度/认证变更是否先确认并同步权威文档；
4. 文档是否一处编写、其余引用，目录索引是否更新；
5. 验证命令与输出是否真实、完整。
输出：阻断项、建议项、未覆盖项，按严重程度排序。
```

## 反模式（不要这样提问）

| 反模式 | 为什么不行 |
| --- | --- |
| 「按上次说的改」 | 上下文不在仓库里，代理无法可靠复现，也无法审计 |
| 「都改一下 / 顺手优化」 | 范围不可验证，容易混入无关改动，违反小步可回滚 |
| 「跳过测试先提交」 | 违反红线；门禁失败等于没有门禁 |
| 「先改前端，后端后面再说」 | 契约顺序错乱，前后端会短暂失配 |
| 「假设某某已经可用」 | 把待确认项当成事实，后续会以错误前提实现 |
| 「只给结论，不用给输出」 | 无法区分「实际通过」与「看起来没问题」 |
