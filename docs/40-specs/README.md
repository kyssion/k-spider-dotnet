# 功能规格

> 状态：已确认
> 最后更新：2026-11-08

本目录回答「某个功能做到什么程度算完成」。规格的写法、状态与索引以本文为准；契约与架构决策见
[20-adr/README.md](../20-adr/README.md)。

## 为什么需要规格

「做一个项目管理页面」这样的描述无法判定完成。规格把需求压缩成可执行的验收断言，让实现者在动手前
就知道边界在哪、什么时候算做完。

## 什么时候写

由改动类型决定，分类表只在 [change-protocol.md](../50-ai/change-protocol.md)「变更分类与所需产物」维护。
一句话：**用户可见行为变化要规格；纯重构、依赖升级、样式微调、文档修订不要。**

## 命名与状态

- 文件名：`NNNN-短横线标题.md`，序号递增，不复用；
- 状态：`草案` → `已确认` → `实现中` → `已实现` / `已取消`（完整词表见
  [docs/README.md](../README.md)「文档状态」）；
- 完成后不删除规格，在文末追加「验收结论」，写明与规格的实际差异；
- 索引表的状态列必须与正文状态行一致；状态为「已实现」的规格必须有「验收结论」。
  两者都由 [check-doc-status.mjs](../../scripts/check-doc-status.mjs) 校验；
- 新增规格后更新本文底部的索引。

## 写法约定

- 每份规格必须写目标、非目标、用户场景、契约、验收标准、边界与异常；
- 规格不重复架构/数据模型定义，只链接权威文档；
- 未确认的范围标【待确认】，并在 [20-adr/README.md](../20-adr/README.md) 的待确认清单登记；
- 验收标准必须可执行，能直接写成测试。

## 模板

```markdown

> 关联 ADR：（如无则写「无」）

## 目标

## 非目标

明确列出本次不做的部分，防止范围蔓延。

## 用户场景

- 作为〈角色〉，我希望〈能力〉，以便〈价值〉。

## 契约

| 项 | 内容 |
| --- | --- |
| 涉及聚合 | |

## 验收标准

- [ ] 当……时，应返回 400 且 `code = validation.xxx`
- [ ] 当……时，列表应包含……且按……排序

## 边界与异常

- 空数据：
- 超长输入：

- 网络失败：

## 验收结论

（实现完成后填写：日期、实际行为与规格的差异、遗留问题）
```
