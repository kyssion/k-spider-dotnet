# 项目定位

> 状态：已确认
> 最后更新：2026-11-08

## 一句话说明

k-spider 是一个「抓取 → 处理 → 展示」的数据平台：crawler 把外部数据站的原始载荷原样抓回
PostgreSQL，process 消费原始载荷并产出结构化数据，web 通过 admin 的同源 API 展示与操作。

## 现状与假设

仓库处于 v2 重建期：v1 相关内容已归档（见根 [README.md](../../README.md) 项目结构），
v2 先落契约、DDL 与文档，服务从骨架逐步实现。因此当前阶段的目标**不是**交付某个具体功能，而是：

1. 把数据链路、调度模型、认证边界与前端入口固定下来；
2. 用可执行的文档与机器守卫代替口头约定；
3. 让后续数据源、处理管线与页面能以「小步、可验证、可回溯」的方式加入。

模块落地状态以根 [README.md](../../README.md) 状态表为准；里程碑见 [roadmap.md](roadmap.md)。

## 目标

- **机制先行，领域克制**：机制按已知变化点抽象；源差异知识只落在 adapter / parser。
- **契约即边界**：模块间只依赖契约，不依赖实现细节。
- **数据与执行状态分离**：业务行存数据语义，执行进度走 `exec_status`，重试细节进 `extra`。
- **一切皆注册**：源、数据集、管线、Job、分析维度、派生表、告警规则都可注册，无手写分支。
- **放开度量，管住成本**：不设硬编码小窗口/只读限制，用预算、血缘、配额管成本。
- **可读性优先**：抽象不为炫技，优先惯用法和成熟模式。

## 非目标

- 不追求 v1 代码、部署单元或旧库结构的兼容；v1 归档只作历史参考。
- 不在采集侧做深解析；解析产物归 process / 分析侧。
- 不预建语义层、查询引擎或物化层；按真实需求立项。
- 不把任何单一 AI agent 的平台特定配置作为仓库约束；技能发现适配器只做路径映射，协作约定走可移植格式。

## 成功标准

| 维度 | 判据 |
| --- | --- |
| 契约可执行 | 数据模型、调度、认证的变更能按文档顺序落地，并在同一次改动中同步 DDL、文档与测试 |
| 新源接入 | 新增数据源只需新增 adapter / parser 并注册，不修改调度与存储主流程 |
| 调度收敛 | admin 重启后能通过节点重连与对账恢复现场，不依赖本地持久状态 |
| 数据可追溯 | 原始载荷在保留期内可达，结构化数据可由原始载荷重放生成 |
| 验证可信 | 任意一次交付都能用实际命令与输出证明结果，而不是「看起来没问题」 |
